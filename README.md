# BMW Wallbox Proxy

Home Assistant add-on repository for a BMW wallbox Modbus smart-meter emulator backed by Home Assistant sensor data.

The proxy answers the Modbus requests generated by the BMW Wallbox and presents the measurements from Home Assistant using the register map expected by the selected meter model.

## Supported meter models

The proxy supports three meter profiles:

| Model | Intended connection | Data format | Default/validated serial settings |
|---|---|---|---|
| `inepro_pro380` | 3-phase | IEEE-754 FLOAT32, ABCD | 9600 8E1, address 1 |
| `inepro_pro2` | **1-phase** | IEEE-754 FLOAT32, ABCD | 9600 8E1, address 1 |
| `janitza_b23` | 3-phase | 32-bit scaled integers | Configure to match the Wallbox |

BMW documents the Inepro Pro 380-MOD for three-phase installations, the Inepro Pro2-MOD for single-phase installations, and the Janitza B23 312-10J for three-phase installations among the supported smart-energy modules for the Gen4 Wallbox. citeturn0search12

The model selected in the proxy must match the **meter model selected in the BMW Wallbox Installation App**. BMW specifies that the meter communication parameters configured in the app should be transferred 1:1 to the smart-energy module. citeturn0search16

### Inepro Pro 380

The `inepro_pro380` profile follows the PRO380 Modbus register layout, including:

- Voltage and current measurements
- Total and per-phase active power
- Reactive and apparent power
- Power factor
- Frequency
- Active/reactive energy registers
- FLOAT32 values in ABCD word order

The implementation uses the documented PRO380 register addresses rather than treating the PRO380 as a generic floating-point meter.

### Inepro Pro2

The `inepro_pro2` profile is specifically for **single-phase** installations. It uses the PRO2 register map and FLOAT32 ABCD encoding.

PRO380-only L2/L3 measurements are returned as zero rather than duplicating L1 values. This is important because the BMW Wallbox must see a genuine single-phase meter profile when the installation is single-phase.

### Janitza B23

The `janitza_b23` profile implements the B23 register layout using the documented scaled 32-bit values:

- Voltage: `0.1 V`
- Current: `0.01 A`
- Active/reactive/apparent power: `0.01 W/var/VA`
- Frequency: `0.01 Hz`

Power values are handled as signed values where required by the B23 map.

The Janitza profile is retained as an available model even when the physical installation uses an Inepro meter profile.

## Install in Home Assistant

1. Open Home Assistant.
2. Go to **Settings → Add-ons → Add-on Store**.
3. Open the three-dot menu and select **Repositories**.
4. Add `https://github.com/AndreasFridh/bmw_wallboxproxy`.
5. Refresh the store and install **BMW Wallbox Proxy**.

The add-on itself lives in [bmw_wallboxproxy/config.yaml](bmw_wallboxproxy/config.yaml) and exposes:

- Home Assistant ingress UI on internal port `8099`
- Modbus/TCP transport on host port `502`

Configure the transport mode, meter model and Home Assistant entity mappings in the Home Assistant add-on configuration panel. The web UI is intended for dashboard and diagnostics.

## Recommended setup with a Waveshare RS485/Ethernet adapter

When using a Waveshare RS485-to-Ethernet adapter as a transparent bridge, the recommended topology is:

```text
BMW Wallbox Gen4
      │
      │ RS485 / Modbus RTU
      │
      ▼
Waveshare RS485 → Ethernet
      │
      │ TCP carrying raw RTU frames
      │
      ▼
bmw_wallboxproxy
```

Use:

```yaml
transport_mode: rtu_over_tcp
```

In this mode the Waveshare device must operate as a **transparent serial/TCP bridge**. Do not configure the Waveshare as a Modbus TCP-to-RTU gateway at the same time as the proxy's `rtu_over_tcp` mode; otherwise the Modbus framing is converted twice.

For an Inepro PRO380/PRO2 installation validated against the meter documentation, use:

```text
9600 baud
8 data bits
Even parity
1 stop bit
Modbus address: 1
```

The BMW Gen4 RS485 interface is documented as:

```text
Pin 8 (CNB12): 485 D+ / Tx+ / Rx+
Pin 9 (CNB12): 485 D- / Tx- / Rx-
```

BMW specifies shielded twisted RS485 wiring for the smart-energy connection. citeturn0search12turn0search16

### Example configuration

```yaml
transport_mode: rtu_over_tcp
meter_model: inepro_pro2
float_word_order: abcd
register_alias_mode: exact
```

For a three-phase PRO380 emulator, change only the model:

```yaml
meter_model: inepro_pro380
```

For a Janitza B23 profile:

```yaml
meter_model: janitza_b23
```

The serial communication parameters must still match the values configured in the BMW Wallbox Installation App and the corresponding physical adapter/meter path.

## Modbus protocol behaviour

The proxy validates incoming RTU frames before responding:

- Modbus RTU CRC is checked.
- Requests for a different slave address are ignored.
- Unsupported/invalid requests are not converted into valid measurement responses.
- Responses are encoded according to the selected meter model.

For example, a PRO380/PRO2 request for L1 current can look like:

```text
01 03 50 0C 00 02 15 08
```

This is slave `1`, function `03`, register `0x500C`, quantity `2` registers, with CRC `15 08`.

For a Janitza B23 installation, the Wallbox uses a different register map. For example, L1 current is requested at `0x5B0C`.

## Phase Mapping

The proxy maps the three phases from your grid meter (L1, L2, L3) to the three phases the wallbox expects. If the wiring order between your grid meter and the wallbox does not match, the charger will read the wrong per-phase power values, which can cause incorrect load management or prevent the back-feeding session from stabilising.

### Symptoms of wrong phase order

- The BMW app shows 0 W total grid power but the per-phase breakdown is clearly unbalanced (e.g. −200 W / +50 W / +150 W).
- The charger throttles or behaves erratically even though total grid power is within limits.
- Back-feeding works but one phase appears to be exporting significantly more than expected.

Note: a sum of zero with unbalanced phases is **not always a mapping problem**. A symmetric charger achieves its target (total = 0) and stops adjusting. The residual per-phase spread is then just normal household load imbalance across phases, which a symmetric charger cannot compensate for.

### How to set the phase order

Open the proxy dashboard, find the **Phase Order** section, and select one of the six buttons (1,2,3 through 3,2,1). The setting is persisted to the env file and survives restarts.

### How to identify the correct phase order without trial and error

1. Note which phase on the grid meter shows the largest negative deviation (that is the phase the charger is back-feeding onto).
2. Check which phase the charger reports as its active output phase (visible in the BMW app or the Home Assistant wallbox integration).
3. Match them: the grid meter phase that swings most = the charger's reported active phase. Use that relationship to determine the full ordering and select the matching button.

Alternatively, if the charger supports a single-phase mode, enable it, start a session, and observe which grid meter phase changes. That phase is charger L1. The remaining two are then found by elimination or by repeating with L2.

### BMW / Starcharge DC bidirectional charger (2026)

The BMW wallbox manufactured by Starcharge uses a **symmetric 3-phase AC/DC stage**. It applies the same current on all three phases simultaneously and cannot control individual phase currents independently.

Practical consequences:

- The charger reads per-phase grid data primarily to detect single-phase overload, not to independently balance each phase.
- It adjusts total charge/discharge power based on the sum of all three phases.
- Once the total reaches the target (typically 0 W net import), the charger holds that rate. Any remaining per-phase spread is household load imbalance and is unaffected by the charger.
- Phase mapping still matters: a wrong mapping can cause the charger to misidentify which phase is overloaded and throttle unnecessarily.

With the correct phase order configured, the charger should run stable back-feeding sessions overnight without intervention.

## Power Offset

The power offset shifts all power readings by a fixed number of watts before they reach the charger. A negative offset makes the charger think the house is exporting more than it really is, so it ramps up charging or back-feeding. A positive offset does the opposite.

The preferred way to control the offset is through a Home Assistant helper entity so you can change it from automations, dashboards, or scripts without touching the proxy add-on.

### Create a helper in Home Assistant

1. Go to **Settings → Devices & Services → Helpers**.
2. Click **Create helper** and choose **Number**.
3. Fill in the form:
   - **Name**: `Wallbox power offset` (or anything you like)
   - **Minimum**: `-10000`
   - **Maximum**: `10000`
   - **Step size**: `100`
   - **Unit of measurement**: `W`
4. Click **Create**.
5. Note the entity ID — it will be something like `input_number.wallbox_power_offset`.

### Wire it to the proxy

1. Open the BMW Wallbox Proxy add-on in Home Assistant.
2. Go to **Configuration**.
3. Set **Power offset entity** to the entity ID from the step above (e.g. `input_number.wallbox_power_offset`).
4. Click **Save** and restart the add-on.

The proxy now polls the helper every second. Changing the helper value in HA immediately flows through to the charger on the next poll.

### Manual override from the dashboard

The proxy dashboard (accessible via the add-on ingress panel) has a **Power offset** card. Typing a value and clicking **Apply override** sets a runtime override that takes precedence over the HA helper. The badge shows which source is active: `Entity` or `Override`.

Clicking **Clear override** removes the manual value and hands control back to the HA helper.

Use the dashboard override when you need a quick temporary adjustment without touching the helper — for example during commissioning or fault investigation.

## Development and tests

The repository includes tests covering the meter-model encoders, register maps, Modbus CRC/protocol handling and model-specific behaviour.

Run the test suite from the repository root with:

```bash
pytest -q
```

The tests specifically cover:

- PRO380 FLOAT32 ABCD encoding and register mapping
- PRO380 energy-register mapping
- PRO2 single-phase behaviour and zeroed L2/L3 registers
- Janitza B23 scaled integer encoding and signed power
- Meter-model dispatch and invalid model handling
- Modbus CRC validation
- RTU-over-TCP request/response handling
- Wrong slave address and invalid CRC handling
- Power-offset behaviour
- Phase/register alias behaviour

## Troubleshooting

### The Wallbox does not detect the meter

Check these in order:

1. **Meter model** in the BMW Installation App matches `meter_model` in the proxy.
2. **Modbus address** matches on both sides (normally `1` for the Inepro profiles).
3. **Baud/parity/data/stop bits** match exactly. For PRO380/PRO2 use `9600 8E1` when using the documented default configuration.
4. Waveshare is in **transparent serial/TCP mode** when the proxy uses `rtu_over_tcp`.
5. RS485 polarity is correct: BMW pin 8 is D+/Tx+/Rx+ and pin 9 is D-/Tx-/Rx-. citeturn0search12
6. Confirm that the Wallbox is actually sending Modbus requests and that the proxy responds with a valid CRC.
7. For a PRO380/PRO2 request, check that the response contains a 4-byte FLOAT32 value in ABCD order.
8. For a Janitza request, check that the response uses the B23 scaled-integer representation rather than FLOAT32.

### Useful diagnostic capture

A healthy PRO380/PRO2 exchange should resemble:

```text
TCP RX  01 03 50 0C 00 02 15 08
TCP TX  01 03 04 XX XX XX XX CRC CRC
```

A Janitza B23 L1-current request should resemble:

```text
TCP RX  01 03 5B 0C 00 02 17 2C
TCP TX  01 03 04 XX XX XX XX CRC CRC
```

If you see repeated requests but no valid responses, check CRC, slave address, model selection and transport mode first.
